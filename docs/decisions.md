## ADR-001: Use Next.js App Router

- **Date**: 2026-08-01
- **Status**: Accepted

### Decision
Use Next.js 15 with the App Router (not the legacy Pages Router).

### Why
- App Router is the current default and long-term direction for Next.js.
- Enables React Server Components (RSC) for server-side data fetching without client-side hydration overhead.
- First-class support for streaming, layouts, loading states, and error boundaries.
- Better integration with `@supabase/ssr` for cookie-based sessions.

### Alternatives Considered
- **Pages Router**: Mature and battle-tested, but being phased out. No RSC support.
- **Remix**: Strong data conventions, but introduces a different ecosystem and learning curve.
- **SvelteKit**: Excellent DX, but outside the locked TypeScript + React ecosystem.

### Tradeoffs
- App Router has a steeper initial learning curve (RSC vs. Client Components mental model).
- Some third-party libraries are not yet fully compatible with RSC â€” requires careful `"use client"` boundaries.

## ADR-002: Supabase Instead of Firebase

- **Date**: 2026-08-01
- **Status**: Accepted

### Decision
Use Supabase as the backend (database, storage, future auth) instead of Firebase.

### Why
- Supabase is built on PostgreSQL â€” a proven, relational database with full SQL support.
- Row-level security (RLS) is native and well-documented.
- Open-source and self-hostable if needed.
- Better TypeScript support via auto-generated types from the schema.
- No vendor lock-in to a proprietary query language (no Firestore query limitations).

### Alternatives Considered
- **Firebase (Firestore)**: Fast to prototype with, but NoSQL makes relational queries awkward. Vendor lock-in. Pricing scales poorly.
- **PlanetScale**: MySQL-based, good DX, but requires separate auth solution.
- **Railway + Postgres**: More control, but more infrastructure to manage.

### Tradeoffs
- Supabase is a managed service â€” some operational decisions are out of our control.
- Cold start latency on free tier edge functions can be noticeable.

## ADR-003: Groq Instead of OpenAI

- **Date**: 2026-08-01
- **Status**: Accepted

### Decision
Use Groq for AI inference instead of OpenAI.

### Why
- Groq provides extremely fast inference speeds (low latency token generation).
- Cost-effective for high-throughput use cases.
- Compatible with the OpenAI SDK interface â€” easy to swap models if needed.
- Free tier is generous for development and prototyping.

### Alternatives Considered
- **OpenAI (GPT-4o)**: Highest capability ceiling, but higher latency and cost. Proprietary.
- **Anthropic (Claude)**: Strong reasoning, good at long-context tasks, but higher cost per token.
- **Google Gemini**: Competitive pricing, but less predictable API stability at time of decision.
- **Local models (Ollama)**: Zero cost, full privacy, but requires hardware and is not suitable for a hosted product.

### Tradeoffs
- Groq's model selection is more limited than OpenAI's.
- Groq is a newer provider â€” long-term reliability and SLA are less battle-tested.
- If a more capable model is needed later, migration to another provider is low-friction (shared SDK interface).

- **Date**: 2026-08-01

### Tradeoffs

## ADR-006: Status-Driven Processing Pipeline

- **Date**: 2026-08-01
- **Status**: Accepted

### Decision
Topics and learning content move through a defined set of statuses (e.g., `pending`, `processing`, `enriched`, `failed`) rather than being processed ad-hoc.

### Why
- Makes processing state explicit and observable â€” easier to debug and monitor.
- Enables idempotent processing: the pipeline can safely re-process items in a known state.
- Decouples ingestion from enrichment â€” each step is independent.
- Natural fit for Supabase row-level queries filtered by status column.

### Alternatives Considered
- **Event-driven (webhooks/queues)**: More scalable but overkill for Phase 0. Can be adopted later.
- **Ad-hoc processing (process on read)**: Simple but unpredictable latency and no visibility into failures.
- **Scheduled batch jobs only**: Predictable but lacks responsiveness for interactive use cases.

### Tradeoffs
- Requires discipline to keep status transitions consistent across the codebase.
- Status column must be indexed for query performance at scale.
- Pipeline logic must handle stuck or orphaned items in intermediate states.

## ADR-007: Design System Source of Truth

- **Date**: 2026-08-01
- **Status**: Accepted

### Decision
`docs/design-system.md` is the single source of truth for all visual decisions. All implementations must match it exactly. No substitutions, enhancements, or personal interpretations are permitted.

### Why
- Ensures visual consistency across the entire product over time.
- Prevents design drift as the team and codebase grow.
- Makes design decisions explicit and reviewable, not hidden in component files.
- When implementation and document conflict, the document always wins â€” forces resolution at the source.

### Alternatives Considered
- **Figma as source of truth**: Visual but not directly auditable. Requires manual inspection to verify implementation.
- **Component code as source of truth**: Leads to implicit decisions buried in class strings with no rationale.
- **Storybook**: Valuable for testing, but is a derivative artifact, not the decision layer.

### Tradeoffs
- Any visual change requires updating `design-system.md` first, adding a step to the workflow.
- Risk of the document becoming stale if edits are made directly to components without updating the doc.

## ADR-008: shadcn `base-nova` Style (Base UI vs Radix UI)

- **Date**: 2026-08-01
- **Status**: Accepted

### Decision
Use the `base-nova` shadcn style, which is built on **Base UI** (`@base-ui/react`) from the MUI team, rather than the default `default` style built on Radix UI.

### Why
- `base-nova` is the most actively developed shadcn style as of 2026.
- Base UI components are headless and accessible, with a clean and minimal API.
- No opinion on styling â€” works naturally with Tailwind v4.
- The `render` prop pattern is more explicit than Radix's `asChild` and avoids prop merging complexity.

### Alternatives Considered
- **shadcn default (Radix)**: Largest community, most online examples. But `base-nova` is the forward-looking choice.
- **shadcn with Headless UI**: Good but less component-rich than Base UI.
- **Custom components from scratch**: Maximum control but significant upfront investment.

### Tradeoffs
- Most shadcn documentation and community examples use Radix. Code must be adapted.
- `asChild` does not exist in Base UI â€” requires `render` prop pattern everywhere.
- State attributes differ: `data-checked`/`data-open`/`data-active` instead of Radix's `aria-*`/`data-state`.

## ADR-009: CSS Design Token Architecture

- **Date**: 2026-08-01
- **Status**: Accepted

### Decision
Define all design tokens as CSS custom properties in `:root` (light) and `.dark` (dark theme), then expose them as Tailwind utilities via `@theme inline` in `app/globals.css`. No values are hardcoded in component files â€” all components consume tokens by name.

### Why
- Single source of truth for all values (no divergence between CSS and Tailwind).
- Dynamic theming works correctly at runtime: changing a CSS var in `.dark` updates the entire UI.
- `@theme inline` avoids redundant CSS variable emission â€” utilities are generated at build time, values are resolved at runtime.
- Tailwind v4 requires this architecture â€” no `tailwind.config.ts` for color definitions.

### Alternatives Considered
- **Hardcode values in components**: Fast to start, impossible to theme consistently.
- **Tailwind `@theme {}` (non-inline)**: Generates duplicate CSS variables alongside `:root` vars â€” redundant and confusing.
- **CSS-in-JS tokens**: Runtime overhead, incompatible with RSC.

### Tradeoffs
- Requires discipline to define tokens in `globals.css` before using them in components.
- Custom properties for radius (`--radius-md`, `--radius-lg`, etc.) must be defined in both `@theme inline` and `:root` to support both utility classes and CSS `var()` usage (e.g., in `rounded-[min(var(--radius-md),10px)]`).

## ADR-010: Server Actions for Email Auth, Client-Side for Google OAuth

- **Date**: 2026-08-01
- **Status**: Accepted

### Decision
Email sign-in, sign-up, and sign-out use Next.js Server Actions (`'use server'`). Google OAuth uses a client-side call to `supabase.auth.signInWithOAuth()`.

### Why
- Server Actions are the natural pattern for form submissions in Next.js App Router. No API route needed.
- `signInWithPassword` and `signUp` have no browser requirement — they can run entirely on the server.
- OAuth providers require a browser redirect to the authorization URL. This **cannot** be initiated from a Server Action.
- Mixing patterns where strictly necessary (Google only) keeps code consistent and server-first everywhere possible.

### Alternatives Considered
- **All client-side**: Simpler mental model, but loses the server-first approach and requires more client-side JS.
- **Route Handlers for all auth**: POST to `/api/auth/...` — more boilerplate, no advantage over Server Actions for this use case.
- **All server actions**: Impossible for OAuth — `signInWithOAuth` must redirect the browser.

### Tradeoffs
- Forms using Server Actions don't show loading state without `useActionState` (React 19). This adds complexity to the client form components.
- Google button must be a client component even though the form can be server-rendered.

## ADR-011: useActionState for Form State Management

- **Date**: 2026-08-01
- **Status**: Accepted

### Decision
Use React 19's `useActionState` hook to connect server actions to client form components. Server actions return typed state objects (`SignInState`, `SignUpState`) on error and call `redirect()` on success.

### Why
- `useActionState` is the React 19 canonical way to track pending state and response from server actions.
- Progressive enhancement: forms work without JS (the action runs as a standard form submission).
- `redirect()` inside a server action throws an error that Next.js catches and handles as a navigation — this works correctly even when called from inside `useActionState`.
- Typed state objects make the error path explicit and type-safe.

### Alternatives Considered
- **URL search params for errors**: Simpler but causes a full page reload on every failed login attempt.
- **useFormState (deprecated)**: Same API, renamed to `useActionState` in React 19.
- **useState + fetch**: Client-side only, loses server-side execution benefits.

### Tradeoffs
- Server actions called via `useActionState` must match the signature `(prevState: S, formData: FormData) => Promise<S>`.

## ADR-012: Plain Text for topics.category (No categories Table)

- **Date**: 2026-08-01
- **Status**: Accepted

### Decision
`topics.category` is a plain `text` column, not a foreign key to a `categories` table.

### Why
- Phase 3 has no UI for browsing/managing categories. A foreign key table adds referential constraints with no application benefit yet.
- Categories are admin-defined and small in number. Text values are practical and searchable via an index.
- Migration from `text` to a FK table is a reversible change. Start simple; add FK if category management becomes a product feature.

### Alternatives Considered
- **`categories` table with FK**: Adds referential integrity, but requires an additional migration, seeding, and admin tooling before any data can be inserted. Premature for Phase 3.

### Tradeoffs
- No database-level constraint prevents typos in category names. Mitigated by admin-controlled inserts via service-role key.
- If a `categories` table is added later, a migration is required to backfill and add the FK.

## ADR-013: Node.js Migration Runner Instead of Supabase CLI

- **Date**: 2026-08-01
- **Status**: Accepted

### Decision
A custom Node.js migration runner (`scripts/migrate.mjs`) using the `postgres` package is used to apply migrations, instead of the Supabase CLI (`supabase db push`).\n\nThe Supabase CLI is still installed as a dev dependency and `supabase/migrations/` uses its standard timestamped filename convention.

### Why
- The Supabase CLI binary is blocked by Windows Defender Application Control (WDAC/AppLocker) on the development machine. Attempts to install via npm (local and global) and via winget all resulted in the binary being blocked.
- The custom runner uses only pure-JavaScript dependencies (`postgres.js`), which are not subject to the same AppLocker restrictions.
- The migration file format (timestamped SQL files) remains Supabase CLI-compatible. If the policy changes or the project moves to a different environment, switching to `supabase db push` requires no migration file changes.

### Alternatives Considered
- **Supabase CLI via npm**: Blocked by AppLocker.
- **winget install Supabase.Supabase**: Package not found in winget registry.
- **Supabase Dashboard SQL Editor**: Not code-tracked; not reproducible.
- **Docker**: Requires Docker Desktop, which may have its own policy restrictions. Overkill for remote-only workflow.

### Tradeoffs
- Custom runner must be maintained as the codebase grows. Minor risk of diverging from Supabase CLI behavior.
- Type generation (`supabase gen types typescript`) is not available. TypeScript types are hand-written instead, which requires manual updates when the schema changes.

## ADR-014: Native Node.js TypeScript for Scripts

- **Date**: 2026-08-01
- **Status**: Accepted

### Decision
Utility scripts (like the database seed script) use Node's native TypeScript support (`--experimental-strip-types`) instead of external executors like `tsx` or `ts-node.

### Why
- Eliminates the need to install external transpilers, reducing dependency bloat.
- Avoids supply chain policy blockers (e.g., AppLocker or pnpm strict mode blocking `esbuild` installation scripts) that frequently occur in restricted Windows environments.
- Provides a fast, built-in way to execute typed scripts in Node v22.6+.

### Tradeoffs
- Requires explicit `.ts` extensions in local script imports (e.g., `import { data } from './data.ts'`).
- Does not perform type checking at runtime (relying on CI/CLI `tsc` checks instead).

## ADR-017: CSS Classes for Component Hover States (No Inline JS Mouse Handlers)

- **Date**: 2026-08-01
- **Status**: Accepted

### Decision
Interactive hover states for Server Components (cards, nav, links) are implemented as CSS classes in globals.css, not as onMouseEnter/onMouseLeave handlers in JSX.\n
### Why
- React Server Components cannot use event handlers (onMouseEnter etc.) because they are rendered on the server and have no client-side React runtime attached.\n- Inline event handlers on Server Components cause hydration warnings and silent failures in production builds.\n- CSS hover (:hover) is pure-CSS and works without JavaScript, making it more resilient and performant.\n
### Tradeoffs
- CSS classes are not as colocated as inline styles. Mitigated by naming conventions (	opic-card, 	opic-card__title, ack-link, etc.) that clearly map to components.

## ADR-018: Single-Topic Discovery UI & Client State Orchestration

- **Date**: 2026-08-01
- **Status**: Accepted

### Decision
We redesigned the home page from a Server-Rendered grid of topics to a Client-Managed single-topic discovery experience. The pp/page.tsx Server Component now fetches basic metadata (id, slug, title, category) for all enriched topics upfront and passes them to a <DiscoveryApp> Client Component. The Client Component handles random topic selection, timer state, mode switching, and microphone permissions without further network requests.

### Why
- The single-topic focus (Unprompted style) demands immediate interactivity (the "Roll" button). Doing this via a server round-trip for every roll would introduce noticeable latency and disrupt the flow.
- Given the small dataset (50 topics), passing the metadata array (only ~5-10KB) to the client on initial load is highly performant and enables instant rolling and filtering by category.

### Tradeoffs
- We move some logic from Server to Client (timers, randomness), increasing client-side bundle slightly.
- Does not scale indefinitely (e.g., if there were 10,000 topics). At that point, we would need to fetch chunks or let the server pick random topics via Server Actions, accepting the latency tradeoff.

## ADR-020: sessionStorage for Ephemeral Session Results

- **Date**: 2026-08-02
- **Status**: Accepted

### Decision
After transcription and AI analysis complete, the result is written to sessionStorage under curio_session_result before navigating to /results. The results page reads and immediately clears it.

### Why
- Transcripts can be thousands of characters — too long for URL query params.
- The result is intentionally ephemeral (no persistence requirement yet).
- sessionStorage is cleared automatically on tab close.
- No database writes, no API round-trips, no client-side state management complexity.
- The results page gracefully redirects to / if the key is missing (direct URL access or after refresh).

### Alternatives Considered
- **URL params**: Transcript too long; hits browser URL length limits (~2KB).
- **localStorage**: Persists across sessions; unnecessary for ephemeral results.
- **React Context / Zustand**: Would require wrapping the entire app in a provider; adds complexity with no benefit for a single-page result.
- **Database storage**: Correct long-term approach (Phase 7), but premature without a session schema.

### Tradeoffs
- Refreshing /results loses the data (redirect to /). Acceptable for a temporary phase; Phase 7 will persist sessions to the database.

## ADR-023: Communication Profile Update Cadence

- **Date**: 2026-08-02
- **Status**: Accepted

### Decision
The communication profile is not regenerated after every session forever. The cadence is:
- Sessions 1–10: regenerate after every session.
- Sessions 11–30: regenerate every 5 sessions.
- Session 31+: regenerate every 10 sessions.

### Why
- Profile regeneration calls the Groq API (non-free). Unbounded calls would be costly.
- In the early sessions, each session provides significant new signal — high update frequency is justified.
- After the first 10 sessions, the profile stabilizes. Less frequent updates are sufficient.
- This mirrors a real mentor relationship: early feedback is frequent, later feedback is periodic.

### Tradeoffs
- A user who does 31+ sessions in a burst will only get a new profile every 10 sessions. Acceptable tradeoff for cost control.

## ADR-024: Session Save is Fire-and-Forget from /results

- **Date**: 2026-08-02
- **Status**: Accepted

### Decision
After reading the session result from sessionStorage, the /results page fires a POST /api/save-session and does not await the response before rendering feedback to the user.

### Why
- The user should see their feedback immediately — no delay waiting for DB writes + AI profile generation.
- Profile updates and letter generation involve AI API calls (1–3 seconds each). Blocking the UI on this would be a poor experience.
- If save-session fails, the user still sees their transcript and feedback. The next session will still work.

### Tradeoffs
- If the user closes the tab before the save completes, the session is lost. Acceptable given the fire-and-forget nature of the current phase.
- Phase 8 can add session persistence to a server-side queue to make this more robust.

## ADR-027: next-themes for Theme Management (Phase 8)

- **Date**: 2026-08-02
- **Status**: Accepted

### Decision
Use 
ext-themes (v0.4.6) to manage Light / Dark / System theme switching. The theme is applied via the .dark class on <html>. Configuration: ttribute="class", defaultTheme="system", enableSystem, disableTransitionOnChange.

### Why
- next-themes is the de-facto standard for theme management in Next.js App Router projects.

- **CSS prefers-color-scheme only**: no user override possible.
- **Custom localStorage hook**: rebuilds what next-themes already provides correctly.

### Tradeoffs
- One additional client-side dependency. Mitigated by next-themes being tiny (~3KB) and zero-config.

## ADR-028: Dark Theme via CSS Custom Properties Only

- **Date**: 2026-08-02
- **Status**: Accepted

### Decision
The dark theme is implemented entirely through updating CSS custom property values in the .dark class block in globals.css. No per-component dark styles. No dark: Tailwind utilities in component JSX.

### Why
- All components already use ar(--foreground), ar(--border), ar(--accent-gold), etc. for every color.
- When .dark is added to <html>, every component instantly inherits the correct dark values without modification.
- This is the correct architectural approach: the design token layer handles theming, components are theme-agnostic.
- Zero risk of missing a component — if it uses tokens, it just works.

### Tradeoffs
- Requires that new components never hardcode colors — they must always reference design tokens.
- Verified: all existing components use CSS custom properties exclusively.
